# Совместная правка договора в OnlyOffice

Закупки, бухгалтерия и юристы правят один договор (docx) одновременно. Каждая
правка остаётся правкой рецензирования с автором, а фон правки красится цветом
отдела автора:

| Кто                          | Роль                  | Цвет фона            |
|------------------------------|-----------------------|----------------------|
| Отдел закупок                | `PURCHASE_DEPARTMENT` | `#C9E7CA` зелёный    |
| Бухгалтерия                  | `ACCOUNTING`          | `#B8EAE6` бирюзовый  |
| Юристы                       | `LEGAL`               | `#E0D2F2` лиловый    |
| Курирующий (профильный) зам  | `PROFILE_DEPUTY`      | `#FFF1A6` жёлтый     |
| Генеральный директор         | `DIRECTOR`            | `#F9C6C6` красный    |

Правит тот, у кого задача на этапе, где заявка стоит сейчас: на «Согласовании
договора» — закупки, бухгалтерия и юристы одновременно, на своём этапе — замы,
на разборе или своей подписи — директор. Отдел — роль задачи, а у замов (их
задача адресована человеку) — пул их этапа.

Код: `PurchaseFileCoEditing` (ключ, конфиг, запись итога, уведомления),
`PurchaseFileEditorController` (открытие, «Сохранить», файл и callback для
Document Server), плагин `docker_env/onlyoffice/plugins/dept-highlighter`,
фронт — `analytics_platform/src/features/Purchases/PurchaseFileEditor.tsx`.

--------------------------------------------------------------------------------

## 1. Как настроить маршрут

Одновременно править могут те, у кого задача на этапе, где заявка стоит
сейчас. Значит, нужен этап с тремя параллельными задачами — в админке
`/purchases/routes`:

    2. Ресёрч и документы     Любой в роли: Отдел закупок      (требует: договор)
    3. Согласование договора  Любой в роли: Отдел закупок      (требует: договор)
                              Любой в роли: Бухгалтерия        (требует: договор)
                              Любой в роли: Юристы             (требует: договор)

На ресёрче закупки прикладывают договор (тип «Договор», .docx). На этапе 3 все
трое открывают его кнопкой «Редактировать» и правят вместе. Этап закрывается,
когда согласуют все трое; юристы и бухгалтерия по-прежнему могут «Вернуть в
отдел закупок».

Остальные участники (и те, кто уже согласовал) открывают тот же документ на
просмотр и видят правки вживую.

--------------------------------------------------------------------------------

## 2. Как это работает

- **Один документ на всех.** Ключ документа — `pf{fileId}r{editorRevision}-{подпись}`
  (`PurchaseFileCoEditing::documentKey`), общий для всех, кто открыл эту
  редакцию. Режим совместной правки — быстрый (`coEditing: fast`), правки
  соавторов видны сразу.
- **Только рецензирование.** Правщик получает `permissions: {edit: false, review: true}`:
  выключить отслеживание изменений нельзя, иначе правка осталась бы без автора и
  без цвета. Принять или отклонить можно только свои правки.
- **Отдел автора** — в `editorConfig.user.group` (название роли). Document Server
  дописывает его к имени: в docx автор правки — «Юристы Козлова Анна» (через
  неразрывный пробел), в интерфейсе редактора префикс скрыт.
- **Цвет отдела** ставит плагин `dept-highlighter`. Каждый участник красит
  фоном цвета своего отдела только свои вставки (правки «добавлено» со своим
  userId): набранное внутри чужой правки перекрашивается в свой цвет. Заливка —
  обычное изменение документа, её сразу видят все и она сохраняется в docx как
  `w:shd`. Сама заливка не становится правкой «Форматирование»: на время покраски
  рецензирование выключается локально. Красит плагин через ~2 с после паузы в
  наборе (чтобы реже спорить с соавтором за абзац) и перепроверяет абзац ещё раз.
- **Удаления не красятся:** редактор рисует их зачёркиванием в цвете автора, а
  заливка на удалённом тексте осталась бы на исходном тексте, если удаление
  отклонят.
- **Ctrl+Z.** Покраска — отдельный шаг отмены. После Ctrl+Z / Ctrl+Y плагин
  замирает, пока человек не начнёт печатать (или 4 секунды), затем докрашивает.
- **«Закрыть» и «Сохранить»** сначала ждут, пока мои правки и их покраска уйдут на
  сервер (до 10 с), и только потом выходят или фиксируют документ.

### Сохранение

| Событие                                    | Callback | Что делаем                                                |
|--------------------------------------------|----------|-----------------------------------------------------------|
| «Сохранить» (наша кнопка или кнопка редактора) | status 6 | Файл в MinIO, сессия продолжается, ключ прежний        |
| Вышел последний участник                   | status 2 | Файл в MinIO, `editorRevision + 1` — следующая сессия под новым ключом |

«Закрыть» просто выводит из сессии: правки уже у остальных и лягут в файл,
когда выйдет последний. Отменить их за всех нельзя, поэтому прежней кнопки
«Отменить» (drop сессии) больше нет.

### Уведомление «договор изменён после согласования»

После сохранения договора (`type = CONTRACT`), если его текст отличается от
лежащего в хранилище (сравнивается `word/document.xml`), — тем, кто уже согласовал
пакет документов (задачи этапов «Ресёрч» и «Согласование» с решением APPROVED),
кроме правивших и тех, у кого ещё открыта задача на текущем этапе: они не
согласовали, а договариваются. Событие `purchase.notification.contract_changed`,
в истории заявки — `CONTRACT_CHANGED`. Подпись при этом не сгорает.

### Адреса для Document Server

Файл (`/purchase_file_editor/{id}/{fileId}/content`) и callback (`…/callback`)
подписаны HMAC по ключу документа, у каждого своя подпись. Адрес callback
получает только правщик — у зрителя его в конфиге нет. Файл из callback
скачивается только из кэша Document Server (`/cache/files/…` на его публичном
или внутреннем адресе, `PurchaseFileEditorController::internalDownloadUrl`):
иначе подделанный callback мог бы читать файлы сервера и внутренние сервисы.

## 3. Развёртывание

1. **Плагин** монтируется в Document Server (уже в `docker-compose.yml`):

       - ./docker_env/onlyoffice/plugins/dept-highlighter:/var/www/onlyoffice/documentserver/sdkjs-plugins/dept-highlighter:ro

   После правки файлов плагина — перезапустить контейнер `onlyoffice`.
   Плагин проверен на Document Server 9.2.1.
2. **Адрес для браузера.** Фронтовый nginx (`analytics_platform/docker_env/nginx/config/default.conf`)
   проксирует `/onlyoffice/` в контейнер `onlyoffice`; у Symfony
   `ONLYOFFICE_DOCUMENT_SERVER_URL=<адрес фронта>/onlyoffice` (например,
   `http://31.133.49.124:8075/onlyoffice`). Отдельный порт наружу не нужен.
3. **Миграция** `Version20260925190000` — колонка `purchase_request_file.editor_revision`.
4. **JWT (рекомендуется).** Без подписи любой, кому договор открыт на просмотр,
   может поправить конфиг в браузере и войти в сессию правщиком под чужим
   отделом. Чтобы включить — в `.env` symfony_documents_flow (его читают и
   Symfony, и docker compose):

       ONLYOFFICE_JWT_ENABLED=true
       ONLYOFFICE_JWT_SECRET=<секрет>

   Document Server получит `JWT_ENABLED`/`JWT_SECRET` из compose, Symfony
   подпишет конфиг редактора и команды и проверит подпись callback
   (`OnlyOfficeJwt`). После смены — `docker compose up -d onlyoffice`.

   ⚠ Document Server общий с редактором шаблонов документов
   (`DocumentCreateFromTemplateController`, `edit_docx.html.twig`), а тот
   подписывать конфиг пока не умеет: с `JWT_ENABLED=true` он перестанет
   открываться. Включать JWT — вместе с его доработкой.

## 4. Ограничения

- Настоящей полупрозрачности нет: в docx у заливки нет альфа-канала, поэтому
  цвета бледные — на белом листе выглядят как маркер.
- Принятая правка остаётся с заливкой отдела (это уже обычный текст): для
  чистового экземпляра заливку нужно снять.
- Если плагин не загрузился (старый кэш браузера) или автор закрыл вкладку
  браузера, не дождавшись покраски, правка всё равно остаётся правкой
  рецензирования с автором — пропадает только цвет.
- Цвет есть у пяти ролей из таблицы. Правки остальных (финансовый директор,
  админ за чужую задачу без роли, автор на поставке) — без заливки; у админа или
  сотрудника с несколькими ролями отдел берётся по роли его задачи на этапе.
- Без JWT правщик, знающий свой адрес callback, может подделать сохранение
  (сам файл он и так вправе менять). Полностью закрывает это только JWT.

# Маршруты согласования закупок — как их составлять

Маршрут отвечает на вопрос «кто и в каком порядке решает по заявке». Собирается
он в админке (`Закупки → Маршруты`, страница `/purchases/routes`), в коде типовых
маршрутов нет и не будет: регламент — это данные, а не константы.

Документ описывает, из чего маршрут состоит, какие правила проверяет редактор и
что нужно сделать, чтобы собранный маршрут начал применяться к новым заявкам.

Базовый путь API: `/spa/api/purchase-routes`

--------------------------------------------------------------------------------

## 1. Заготовка и снимок — два разных объекта

Это главное, что нужно понять до всего остального.

    Заготовка (шаблон)  Регламент: «обычная закупка идёт так». Одна строка на
                        весь справочник, правится в админке в любой момент.

    Снимок              Копия заготовки внутри конкретной заявки, сделанная в
                        момент подачи. Дальше живёт отдельно: заявка идёт по
                        тому регламенту, который действовал, когда её подали.

Отсюда два следствия, которые чаще всего удивляют:

- **Правка заготовки не трогает заявки в пути.** Исправили маршрут — новый
  порядок увидят только заявки, поданные после правки. Версий у заготовки нет:
  снимок и есть версия.
- **Повторная подача пересобирает снимок заново** — по нынешней заготовке, а не
  по той, что действовала в первый раз. Заявку вернули на доработку, состав и
  сумма изменились, регламент могли поправить — согласовывать надо то, что есть.

Код: `ApprovalRouteBuilder` (сборка снимка), `ApprovalRouteEditor` (правка
заготовок), `ApprovalRouteResolver` (выбор заготовки для заявки).

--------------------------------------------------------------------------------

## 2. Из чего собран маршрут

Два уровня:

    Этап (stage)   Шаг маршрута. Заявка стоит ровно на одном этапе.
      Задача (task)  Чьё-то решение внутри шага.

**Последовательность — это разные этапы. Параллельность — это несколько задач в
одном этапе.** Этап закрывается, когда закрыты все его задачи; подписи внутри
этапа ложатся в любом порядке.

Номера позиций считает бэк по порядку списка — фронт их не присылает, и вручную
проставлять ничего не нужно. Порядок этапов = порядок в редакторе.

Заготовка целиком заменяется при каждом сохранении: частичных правок нет, потому
что порядок этапов и состав задач — свойства всего маршрута.

--------------------------------------------------------------------------------

## 3. Назначение этапа

Поле «Назначение» (`purpose`) — не ярлык, оно меняет поведение:

| Значение   | В интерфейсе        | Что даёт                                                                                |
|------------|---------------------|-----------------------------------------------------------------------------------------|
| `TRIAGE`   | Разбор заявки       | Даёт очередь разбора (модалка директора): правки состава, назначение согласантов, смена маршрута, вердикт. В маршруте не больше одного |
| `SOURCING` | Ресёрч и документы  | Закрывший становится **исполнителем** заявки. Этап — граница возврата: идущие следом возвращают заявку сюда, а не автору |
| `SIGN_OFF` | Согласование        | Обычная подпись: смотрят готовый пакет и решают                                          |
| `PAYMENT`  | Оплата              | По закрытии заявка получает статус `INVOICE_PAID`                                        |
| `DELIVERY` | Поставка            | По закрытии — `DELIVERED`                                                                |
| `CLOSING`  | Закрытие            | По закрытии — `DONE`, заявка уходит в архив                                              |

Первые три — согласующая часть, последние три — исполнение. Пока идёт
согласующая часть, статус заявки `ON_APPROVAL`; когда она кончилась — `APPROVED`.
Если исполнения в маршруте нет, заявка так и останется в `APPROVED`, и это
законная настройка.

--------------------------------------------------------------------------------

## 4. Адресат задачи

| Значение        | В интерфейсе             | Кто закроет                                          |
|-----------------|--------------------------|------------------------------------------------------|
| `ROLE`          | Любой в роли             | Любой носитель выбранной роли модуля                 |
| `DYNAMIC_USERS` | Кого выберет разбирающий | Люди, которых директор отметит на разборе            |
| `AUTHOR`        | Автор заявки             | Тот, кто подал заявку                                |

Поимённо сотрудников в заготовку не вписывают — только роли. Сотрудник уходит в
отпуск, меняет отдел и увольняется, а маршрут остаётся: заявки встали бы на
человеке, которого уже нет. Нужен ровно один подписант — заведите роль с одним
носителем, состав носителей меняется в справочнике согласантов.

Роль **«Профильный зам» нельзя выбрать адресатом** `ROLE`: её смысл обратный —
замов подбирают под конкретную заявку. Она законна как **пул** динамического
этапа.

--------------------------------------------------------------------------------

## 5. Динамический этап

Этап, задача которого адресована «кого выберет разбирающий». В заготовке в нём
стоит одна задача-место с пулом ролей (`candidateRoleCode`), людей там нет.

Как он живёт:

1. При подаче в снимке появляется пустой этап в статусе `AWAITING_ASSIGNMENT` —
   в карточке видно «ожидает назначения».
2. На разборе директор выбирает людей из пула. Каждый выбранный получает свою
   задачу; порядок соседних этапов при этом не двигается.
3. Если разбирающий не выбрал никого, этап помечается `SKIPPED` — маршрут не
   должен вставать в ожидании тех, кого не будет.

Ограничения: в динамическом этапе ровно одна задача (ролевые рядом стоять не
могут — этап нельзя было бы ни закрыть, ни показать как ожидающий), и стоять он
обязан **строго после разбора** — иначе назначать людей некому.

Автор заявки в согласанты не попадает никогда, дубли выбора склеиваются.

--------------------------------------------------------------------------------

## 6. Остальные поля

**Заголовок этапа** — необязательный. Пустой заголовок не проблема: карточка
подставит адресатов задач («Бухгалтерия и Юристы»), а у динамического — название
пула.

**Разрешён отказ** (`allowsReject`) — можно ли с этого этапа вернуть заявку
автору. По умолчанию включён у согласующих этапов и выключен у исполнения: после
оплаты «вернуть автору» означало бы не решение по заявке, а потерянные деньги.

**Требуемый документ** (`requiresFileType`) — задачу нельзя согласовать, пока к
заявке не приложен файл этого типа (`PURCHASE_TASK_FILE_REQUIRED`). Требование
живёт на задаче, а не в конвейере: у быстрого маршрута задачи «договор» нет, и
требовать с него договор не за что. Типы: техническое задание
(`TECHNICAL_SPEC`), договор (`CONTRACT`), УПД (`UPD`), прочее (`OTHER`).

**Виды заявки** (`allowedKinds`) — по каким кнопкам создания заявка вправе пойти
этим маршрутом: быстрая, обычная или обе.

--------------------------------------------------------------------------------

## 7. Правила, которые редактор не даст нарушить

`ApprovalRouteEditor::assertRulesHold()` и `parseStages()`:

| Правило                                                        | Код ошибки                            |
|----------------------------------------------------------------|---------------------------------------|
| Маршрут не пустой                                              | `PURCHASE_ROUTE_EMPTY`                |
| Этап не пустой (хотя бы одна задача)                           | `PURCHASE_ROUTE_STAGE_INVALID`        |
| В динамическом этапе только одна задача                        | `PURCHASE_ROUTE_STAGE_INVALID`        |
| Разбор в маршруте не больше одного                             | `PURCHASE_ROUTE_STAGE_ORDER_INVALID`  |
| Динамический этап — строго после разбора                       | `PURCHASE_ROUTE_STAGE_ORDER_INVALID`  |
| Исполнение — после всех согласующих этапов                     | `PURCHASE_ROUTE_STAGE_ORDER_INVALID`  |
| Задача «Автор заявки» — только в исполнительном этапе          | `PURCHASE_ROUTE_TASK_INVALID`         |
| Адресат «конкретный сотрудник» в заготовке запрещён            | `PURCHASE_ROUTE_TASK_INVALID`         |
| Код заготовки уникален                                         | `PURCHASE_ROUTE_CODE_TAKEN`           |

Разбор при этом **не обязателен**. Маршрут без него законен — просто заявки по
нему идут мимо очереди директора, и динамических этапов в нём быть не может.

--------------------------------------------------------------------------------

## 8. Как заявка идёт по собранному маршруту

- Указатель хранится: активный этап помечен статусом, а не вычисляется из
  решений. Двое согласантов одного этапа, нажавших одновременно, не мешают друг
  другу — запись идёт под оптимистичной блокировкой, второй повторяет с
  актуальными данными.
- Этап закрывается, когда **все** его задачи согласованы, и указатель уходит
  дальше.
- Отказ (если этап его разрешает) переводит заявку в `REJECTED` — «возвращено на
  доработку», автор правит и подаёт заново.
- «Вернуть в отдел закупок» доступно, только если в маршруте есть этап `SOURCING`
  и он стоит **раньше** текущего. Заявка откатывается на него, а решения,
  успевшие лечь после, сбрасываются: пакет документов будет другой.
- Отзыв своей подписи возможен только на согласующей части — на исполнении через
  подпись прошли деньги.

--------------------------------------------------------------------------------

## 9. Очередь разбора: когда директор увидит заявку

Кнопка «Разбор новых заявок (N)» активна, а модалка что-то показывает, только
когда заявка попала в `GET /spa/api/purchases/director-queue`. Условия — все
сразу:

1. статус заявки `ON_APPROVAL` (создана ≠ подана: `create` оставляет `DRAFT`);
2. в снимке есть этап `TRIAGE` **и** заявка стоит именно на нём (`ACTIVE`);
3. в этапе есть нерешённая задача;
4. задача адресована этому человеку — лично, его ролью модуля, или он автор
   заявки при задаче типа «Автор».

Ролевого гейта «ты директор» в бэке нет намеренно: очередь и есть ответ на
вопрос «что ждёт меня». Директор здесь — тот, кому маршрут адресовал разбор.

Очередь запрашивается один раз при открытии страницы: заявку подали при открытой
вкладке — нужна перезагрузка. Ошибка запроса выглядит так же, как пустая очередь.

--------------------------------------------------------------------------------

## 10. Чек-лист: собрал маршрут — что дальше

Три шага, без которых маршрут не применяется. О них забывают чаще, чем ошибаются
в этапах.

1. **Включить маршрут.** Создаётся и копируется он выключенным намеренно:
   маршрут, появившийся в списке выбора готовым к работе, — это регламент,
   который никто не просматривал.
2. **Назначить маршрутом по умолчанию для вида заявки** — блок «По умолчанию» на
   той же странице. Умолчаний в коде нет: вид заявки без дефолта вообще нельзя
   подать, резолвер вернёт `PURCHASE_ROUTE_NOT_CONFIGURED`.
3. **Выдать роли людям** в справочнике согласантов. Маршрут адресует задачу роли;
   если роль никому не выдана, заявка встанет на этапе, которого никто не видит.

Проверка: кнопка «Превью» у маршрута (`GET /spa/api/purchase-routes/{id}/preview`)
считает теми же резолвером и сборщиком, что и реальная подача, — показывает
именно то, что получится. Дальше — подать одну заявку и убедиться, что она встала
у нужного человека.

Править маршруты может только `ROLE_ADMIN`.

--------------------------------------------------------------------------------

## 11. Примеры

**Обычная закупка с разбором**

    1. Разбор заявки        Любой в роли: Директор
    2. Ресёрч и документы   Любой в роли: Отдел закупок      (требует: договор)
    3. Согласование         Кого выберет разбирающий: Профильный зам
    4. Согласование         Любой в роли: Финансовый директор
    5. Оплата               Любой в роли: Бухгалтерия
    6. Поставка             Автор заявки
    7. Закрытие             Любой в роли: Бухгалтерия        (требует: УПД)

Этап 3 — динамический, поэтому обязан идти после разбора. Этапы 5–7 —
исполнение, поэтому только после всех согласующих.

**Быстрая закупка без разбора**

    1. Ресёрч и документы   Любой в роли: Отдел закупок
    2. Согласование         Любой в роли: Финансовый директор
    3. Оплата               Любой в роли: Бухгалтерия

Динамических этапов здесь быть не может, и в очередь директора такие заявки не
попадают.

**Параллельное согласование** — две задачи в одном этапе:

    3. Согласование         Любой в роли: Юристы
                            Любой в роли: Бухгалтерия

Заявка уйдёт дальше, когда подпишут обе стороны, в любом порядке.

--------------------------------------------------------------------------------

## 12. Частые ошибки

| Симптом                                              | Причина                                                              |
|------------------------------------------------------|----------------------------------------------------------------------|
| У директора «Заявок на разбор нет»                   | Заявки в `DRAFT`; или в маршруте нет `TRIAGE`; или роль не выдана     |
| Заявку нельзя подать, `PURCHASE_ROUTE_NOT_CONFIGURED`| Для вида заявки не назначен дефолт, либо маршрут выключен или пуст    |
| Заявка встала и никого не ждёт                       | Этап адресован роли, у которой нет носителей                          |
| Правка маршрута «не подействовала»                   | Заявки в пути идут по своему снимку — правка касается только новых     |
| Редактор не сохраняет, `..._STAGE_ORDER_INVALID`     | Динамический этап раньше разбора, второй разбор, или исполнение раньше согласования |

--------------------------------------------------------------------------------

## 13. API

Все ручки правки — под `ROLE_ADMIN`, тело и ответ — JSON.

| Метод и путь                              | Назначение                                  |
|-------------------------------------------|---------------------------------------------|
| `GET /spa/api/purchase-routes`            | Список заготовок, дефолты и справочники выбора |
| `POST /spa/api/purchase-routes`           | Создать (по умолчанию выключена, если не прислан `isActive`) |
| `PUT /spa/api/purchase-routes/{id}`       | Заменить заготовку целиком                  |
| `POST /spa/api/purchase-routes/{id}/clone`| Копия со всеми этапами                      |
| `PATCH /spa/api/purchase-routes/{id}/active` | Включить/выключить: `{"isActive": true}` |
| `PUT /spa/api/purchase-routes/defaults`   | Дефолт для вида: `{"kind", "templateId"}`   |
| `GET /spa/api/purchase-routes/{id}/preview` | Что получится при подаче                  |

Тело создания и правки:

```json
{
  "name": "Обычная закупка",
  "code": "STANDARD",
  "description": "Маршрут по умолчанию для обычных заявок",
  "allowedKinds": ["STANDARD"],
  "sortOrder": 10,
  "isActive": true,
  "version": 7,
  "stages": [
    {
      "purpose": "TRIAGE",
      "title": null,
      "allowsReject": true,
      "tasks": [
        { "assignmentType": "ROLE", "roleCode": "DIRECTOR" }
      ]
    },
    {
      "purpose": "SIGN_OFF",
      "tasks": [
        { "assignmentType": "DYNAMIC_USERS", "candidateRoleCode": "PROFILE_DEPUTY" }
      ]
    },
    {
      "purpose": "DELIVERY",
      "allowsReject": false,
      "tasks": [
        { "assignmentType": "AUTHOR", "requiresFileType": "UPD" }
      ]
    }
  ]
}
```

`version` при правке обязателен (`PURCHASE_ROUTE_VERSION_REQUIRED`, если его нет)
— это защита от одновременной правки двумя админами: если заготовку успели
изменить, ответ будет `PURCHASE_CONCURRENT_UPDATE`, нужно перечитать и повторить.
`position` не присылается — порядок задаёт сам список.

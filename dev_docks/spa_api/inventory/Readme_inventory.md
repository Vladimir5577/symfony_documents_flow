# SPA API — Инвентаризация ТМЦ

Учёт имущества по организациям: справочник видов товара, справочник категорий,
привязки администраторов, карточки позиций с назначением на сотрудников,
статусами и журналом движений.

Базовый путь: `/spa/api/inventory`

## Вид товара и позиция — два разных объекта

Модель двухуровневая, и это главное, что нужно понять перед чтением остального.

    Вид товара (номенклатура)   «Монитор RDW2401K». Одна строка на весь
                                справочник. Держит наименование и категорию.

    Позиция                     Конкретный монитор с инвентарным номером
                                ОС-000451 у Иванова. Их тридцать две, у каждой
                                свой номер, статус и владелец. Наименования
                                своего нет — берётся с вида.

Раньше наименование было свободной строкой у каждой позиции, и один и тот же
монитор заводили как «Монитор RDW2401K» и «Монитор RDW 2401К, 23.8» — посчитать
уникальные товары или найти их одним запросом было нельзя. Теперь наименование
редактируется только у вида, а позицию можно лишь перевести на другой вид
(п. 11). Количества в справочнике нет: десять мониторов — это десять позиций
с одним `nomenclature.id`.

Категория тоже переехала на вид: разные категории означают разные виды. В объекте
позиции `category` по-прежнему приходит, но приходит с вида и через `PATCH`
позиции не меняется.

--------------------------------------------------------------------------------

## Авторизация

Все запросы — с JWT в заголовке:

    Authorization: Bearer <token>

Токен получается через `POST /spa/api/login_check` (см.
`dev_docks/spa_api/user/Readme_spa_auth.txt`).

Почти весь модуль закрыт ролью `ROLE_INVENTORY_MANAGER`; `ROLE_INVENTORY_ADMIN`
и `ROLE_ADMIN` проходят через иерархию ролей. Исключений два: раздел «Мои товары»
доступен любому аутентифицированному сотруднику, а удаление позиции (п. 17)
требует `ROLE_ADMIN` — роли инвентаризации, включая главного администратора
модуля, туда не пускают.

    401  нет или невалидный токен
    403  нет роли инвентаризации либо товар вне зоны видимости

## Модель доступа

Ролей две, и они означают разное. `ROLE_INVENTORY_ADMIN` — полный доступ сам по
себе, без всяких привязок. `ROLE_INVENTORY_MANAGER` пускает в модуль, а что
именно видно — определяют строки в `inventory_access`.

    Главный администратор      ROLE_INVENTORY_ADMIN (или ROLE_ADMIN — через
      инвентаризации           иерархию). Видит все товары во всех организациях,
                               ведёт справочник категорий, раздаёт доступы кому
                               угодно и куда угодно. Строк в inventory_access
                               не имеет и не требует.

    Админ организации          ROLE_INVENTORY_MANAGER + строка с category = null.
                               Видит всю свою организацию вместе с дочерними,
                               все категории.

    Ответственный за категорию ROLE_INVENTORY_MANAGER + строка с заполненной
                               category. Видит в своём поддереве только товары
                               этой категории.

    Сотрудник                  ролей инвентаризации не имеет. Только «Мои
                               товары», на чтение.

Иерархия в `security.yaml`:

    ROLE_ADMIN:              [..., ROLE_INVENTORY_ADMIN, ROLE_USER]
    ROLE_INVENTORY_ADMIN:    [ROLE_INVENTORY_MANAGER, ROLE_USER]
    ROLE_INVENTORY_MANAGER:  ROLE_USER

`ROLE_INVENTORY_MANAGER` выдаётся вместе с первой привязкой и снимается вместе
с последней — это делает `AccessController`, больше нигде она не появляется.

Роль здесь — кэш привязок для гейта контроллеров и бокового меню, а не источник
прав. Выводить её на лету из `inventory_access` пробовали и отказались: метод
`User::getRoles()` вызывается на каждом запросе stateless-файрвола, и модуль
добавлял бы лишний SELECT всему приложению, включая тех, кто инвентаризацию
не открывает. Настоящие права всё равно считает `InventoryScope`, поэтому
устаревшая роль пускает максимум на пустой экран.

`ROLE_INVENTORY_ADMIN` — обычная хранимая роль, её выдаёт общий администратор
системы через управление пользователями.

Привязка распространяется на всю ветку дерева организаций: выдали доступ к
организации — видны и её филиалы с департаментами.

Права по операциям:

    просмотр, создание, назначение, снятие, смена статуса, правка карточки
        — админ организации и ответственный за категорию (в своей зоне)

    перенос в другую организацию, смена вида товара
        — только админ организации; при переносе он должен быть админом
          и в организации-источнике, и в организации-получателе

    создание, правка и удаление видов товара и категорий
        — только ROLE_INVENTORY_ADMIN

    удаление позиции
        — только ROLE_ADMIN, главному администратору инвентаризации закрыто.
          Обычное выбытие имущества это статус written_off, а не удаление (п. 17)

Чтение справочника видов открыто всем с ролью `ROLE_INVENTORY_MANAGER`: вид
обязателен при заведении позиции, и без списка выбирать было бы не из чего.

Выдавать и отзывать привязки может главный администратор (в любой организации)
и админ организации (в своём поддереве).

## Формат ответов

    Список товаров:   { "items": [...], "pagination": {...}, "filters": {...} }
    Мои товары:       { "items": [...], "pagination": {...} }
    Один товар:       { "item": {...} }        — и после любой операции
    Виды товара:      { "nomenclature": [...] } / { "nomenclature": {...} }
    Категории:        { "categories": [...] }  / { "category": {...} }
    Привязки:         { "access": [...], "canManage": true } / { "access": {...} }
    История:          { "history": [...] }
    Справочники:      { "organizations": [...] } / { "users": [...] }
    Список УПД:       { "upd": [...], "pagination": {...}, "canManage": true }
    Карточка УПД:     { "upd": {...}, "files": [...] }
    Один УПД:         { "upd": {...} }         — после создания и правки
    Файл УПД:         { "file": {...} }        — после загрузки
    Удаление:         { "success": true }
    Ошибка:           { "error": "машинный_код" }

Внимание: в `error` приходит машинный код (snake_case), а не готовый текст для
пользователя. Подписи к кодам держит фронт. Полный список — в конце документа.

Ещё внимание: у документов ключ называется `upd` и в списке, и в карточке, но
в списке это массив, а в карточке — объект. Ключа `items` у списка УПД нет,
в отличие от списка товаров. То же самое у видов товара: `nomenclature` —
массив в списке и объект в ответе на создание и правку.

`canManage` есть у двух списков — привязок и документов. Он отвечает на вопрос
«показывать ли кнопку создания»: ответственный за категорию проходит в оба
раздела по роли, но список у него пуст, а создание вернёт 403.

Пагинация одинаковая с остальным SPA API:

    "pagination": {
      "current_page": 1,
      "total_pages": 7,
      "total_items": 132,
      "items_per_page": 20
    }

Даты — ISO 8601 (`createdAt`, `updatedAt`), кроме `purchasedAt`: там `YYYY-MM-DD`.
Денежные значения приходят строкой с двумя знаками после точки.

Организация везде приходит объектом с `path` — путём от корня дерева через ` / `:
«ДонСтройМаш / Северный филиал / Бухгалтерия». Одного `name` в списках мало,
отделы в разных филиалах называются одинаково. У корневой организации `path`
совпадает с `name`.

## Статусы товара

    in_stock       На складе
    in_use         В работе
    under_repair   В ремонте
    written_off    Списан

Списание — обычная смена статуса, товар остаётся в базе с историей. Владелец
при списании автоматически не снимается: это делает человек отдельным действием.

## 1. Виды товара (номенклатура)

    GET /spa/api/inventory/nomenclature

Справочник общий на всю компанию: по организациям не делится, видят его все
с ролью инвентаризации. Ответ отсортирован по наименованию.

Query-параметры (оба опциональны):

    search   подстрока в наименовании, регистр не важен: «RDW» найдёт
             «Монитор RDW2401K»
    limit    потолок строк, 1…100. Без параметра приходит весь справочник

Без параметров ручка отдаёт всё — так её зовёт экран справочника. Пикер вида
в форме позиции шлёт `search` и `limit` и спрашивает заново на каждый набранный
запрос: тянуть сотни строк ради одного выбора незачем.

    {
      "nomenclature": [
        { "id": 12, "name": "Монитор RDW2401K", "category": { "id": 1, "name": "Оргтехника" },
          "total": 32, "assigned": 27 },
        { "id": 31, "name": "Стол письменный",  "category": null,
          "total": 0,  "assigned": 0 }
      ]
    }

`total` — сколько штук этого вида заведено, `assigned` — сколько из них закреплено
за сотрудниками. Разница между ними и есть склад: «на складе» — это отсутствие
владельца, а не статус. **Списанные ни в одно из чисел не входят**: вопрос «сколько
у нас мониторов» — про то, чем можно пользоваться, а списанный остаётся в базе
только ради истории.

Оба поля приходят **только `ROLE_INVENTORY_ADMIN`** — экран справочника его.
Менеджеру список нужен пикером в форме позиции, там числа лишние, а заодно они
не раскрывают количества по всей компании тому, кто ведёт одну организацию.

Считаются одним запросом с группировкой на весь список, а не по запросу на вид:
справочник живёт сотнями строк, и счёт в цикле стоил бы сотни SELECT-ов на открытие
экрана.

`category: null` — вид ещё не разобран. Следствие то же, что раньше было
у позиции без категории: такой вид не входит в зону ответственного за категорию,
и завести по нему позицию может только админ организации.

### Создание

    POST /spa/api/inventory/nomenclature       только ROLE_INVENTORY_ADMIN

Тело:

    {
      "name": "Монитор RDW2401K",
      "categoryId": 1                // необязательно, категория должна быть активна
    }

    201  { "nomenclature": {...} }
    400  inventory_nomenclature_name_required
    404  inventory_category_not_found
    409  inventory_nomenclature_name_exists    имя занято
    409  inventory_category_not_allowed        категория архивная

Имя уникально **без учёта регистра**: «Монитор Dell» и «монитор dell» — один и
тот же вид, второй не создать. Ровно ради этого справочник и заводился.

При конфликте в теле приходит найденный вид — чтобы фронт мог предложить выбрать
его, а не заставлять пользователя гадать, что именно совпало:

    { "error": "inventory_nomenclature_name_exists",
      "nomenclature": { "id": 12, "name": "Монитор Dell", "category": {...} } }

Регистром дело и ограничивается. Опечатка («Клавиатура компьтерная» против
«компьютерная») и латинская `K` вместо кириллической `К` пройдут как разные виды —
индекс их не различает, сводить такие пары придётся руками.

### Изменение

    PATCH /spa/api/inventory/nomenclature/{id}  только ROLE_INVENTORY_ADMIN

Тело — любое подмножество:

    { "name": "Монитор RDW2401K 23.8", "categoryId": null }

`categoryId: null` снимает категорию, возвращая вид в неразобранные.

    200  { "nomenclature": {...} }
    404  inventory_nomenclature_not_found | inventory_category_not_found
    409  inventory_nomenclature_name_exists | inventory_category_not_allowed

Смена категории у вида не пишет историю позициям: их могут быть тысячи, и лента
каждой заполнилась бы событием, которого никто не совершал. Новая категория
начинает действовать сразу — включая фильтры и права доступа.

### Удаление

    DELETE /spa/api/inventory/nomenclature/{id} только ROLE_INVENTORY_ADMIN

    200  { "success": true }
    404  inventory_nomenclature_not_found
    409  inventory_nomenclature_has_items      по виду заведены позиции

При отказе в теле приходит счётчик:

    { "error": "inventory_nomenclature_has_items", "itemsCount": 32 }

Удалить вид вместе с его имуществом одним запросом нельзя — порядок строго
такой: сначала позиции по одной (п. 17), потом опустевший вид. Освободить вид,
сохранив имущество, можно переводом позиций на другой вид (п. 11); операции
слияния двух видов пока нет — см. «Чего пока нет».

## 2. Категории

    GET /spa/api/inventory/categories

Query-параметры:

    only_active   1 — вернуть только активные (для форм создания товара)

Ответ:

    {
      "categories": [
        { "id": 1, "name": "Оргтехника", "isActive": true },
        { "id": 4, "name": "Мебель",     "isActive": true }
      ]
    }

Справочник заводится с нуля: предустановленных категорий нет, все создаёт
главный администратор. Категория висит на виде товара, а не на позиции, и может
отсутствовать — см. фильтр `no_category` в п. 4.

`isActive: false` — категория архивная: не предлагается при заведении новых видов
товара, но существующие виды в ней остаются и продолжают отображаться.

### Создание

    POST /spa/api/inventory/categories        только ROLE_INVENTORY_ADMIN

Тело:

    { "name": "Мебель" }

    201  { "category": { "id": 4, "name": "Мебель", "isActive": true } }
    400  inventory_category_name_required
    409  inventory_category_name_exists

### Изменение

    PATCH /spa/api/inventory/categories/{id}   только ROLE_INVENTORY_ADMIN

Тело — любое подмножество полей:

    { "name": "Мебель офисная", "isActive": false }

    200  { "category": {...} }
    409  inventory_category_name_exists

### Удаление

    DELETE /spa/api/inventory/categories/{id}  только ROLE_INVENTORY_ADMIN

    200  { "success": true }
    409  inventory_category_has_items          в категории есть виды товара
                                               или позиции, либо назначен
                                               ответственный

При отказе из-за непустой категории в теле приходят три счётчика:

    { "error": "inventory_category_has_items",
      "itemsCount": 42, "nomenclatureCount": 3, "responsibleCount": 1 }

`nomenclatureCount` считается отдельно от `itemsCount`: вид без единой позиции
всё равно держит категорию внешним ключом, и без этой проверки наружу ушла бы
сырая ошибка драйвера вместо 409.

Чтобы освободить категорию, переведите её виды в другую (п. 1). Если категория
просто больше не нужна — не удаляйте, а поставьте `isActive: false`.

## 3. Привязки администраторов

    GET /spa/api/inventory/access

Главный администратор видит все привязки, админ организации — только привязки
своего поддерева. Ответственный за категорию получит пустой список: управлять
доступами он не может.

Ответ:

    {
      "access": [
        {
          "id": 3,
          "user": {
            "id": 51, "lastname": "Иванов", "firstname": "Пётр",
            "patronymic": "Сергеевич", "login": "ivanov_ps"
          },
          "organization": {
            "id": 2, "name": "ДонСтройМаш", "fullName": "ООО «ДонСтройМаш»",
            "path": "ДонСтройМаш"
          },
          "category": { "id": 1, "name": "Оргтехника" },
          "isOrganizationAdmin": false,
          "createdBy": { "id": 1, "login": "admin" },
          "createdAt": "2026-08-03T10:15:00+03:00"
        }
      ],
      "canManage": true
    }

`category: null` вместе с `isOrganizationAdmin: true` — админ организации.
Заполненная `category` — ответственный за эту категорию.

`canManage` — может ли текущий пользователь выдавать и отзывать привязки хоть
где-нибудь. У ответственного за категорию он `false`: роль пускает его на экран,
но список пуст, а выдача вернёт 403. Фронту флаг нужен, чтобы не показывать
кнопку, обречённую на отказ, — отличить админа организации от ответственного
по одной роли нельзя.

### Выдача

    POST /spa/api/inventory/access

Тело:

    {
      "userId": 51,
      "organizationId": 2,
      "categoryId": 1          // не передавать или null — сделать админом организации
    }

    201  { "access": {...} }
    403  inventory_organization_not_allowed   организация вне вашей зоны
    404  user_not_found | organization_not_found | inventory_category_not_found
    409  inventory_access_exists              такая привязка уже есть

### Изменение зоны ответственности

    PATCH /spa/api/inventory/access/{id}

Тело:

    {
      "categoryId": 1          // не передавать или null — сделать админом организации
    }

Меняется только зона ответственности. Сотрудника и организацию через правку не
переносят: это не изменение одной привязки, а отзыв доступа у одного человека
и выдача другому — делается отзывом и новой выдачей.

    200  { "access": {...} }   — и когда менять нечего, зона совпала
    403  access_denied                          организация вне вашей зоны
    404  inventory_access_not_found | inventory_category_not_found
    409  inventory_access_exists                такая привязка у сотрудника уже есть

### Отзыв

    DELETE /spa/api/inventory/access/{id}

    200  { "success": true }
    403  access_denied
    404  inventory_access_not_found

Отзыв последней привязки снимает с сотрудника роль `ROLE_INVENTORY_MANAGER`,
выдача первой — возвращает. Роль сопровождается только здесь.

## 4. Список товаров

    GET /spa/api/inventory/items

Query-параметры (все опциональны):

    page                  номер страницы, по умолчанию 1
    page_size             размер страницы, по умолчанию 20, максимум 100
    organization_id       фильтр по организации
    only_own_organization 1 — без дочерних организаций (по умолчанию с ними)
    category_id           фильтр по категории (категория берётся с вида)
    no_category           1 — только позиции, чей вид без категории
    nomenclature_id       все позиции одного вида товара
    status                in_stock | in_use | under_repair | written_off
    upd_id                позиции, приехавшие по документу (см. п. 16)
    assigned_to_id        товары конкретного сотрудника
    unassigned            1 — только не присвоенные никому
    assignee_fired        1 — товары, закреплённые за уволенными сотрудниками
    search                по наименованию вида, инвентарному и серийному номеру
    sort                  id | name | inventoryNumber | status | createdAt
                          по умолчанию createdAt; name — по наименованию вида
    direction             ASC | DESC, по умолчанию DESC

`nomenclature_id` отвечает на вопрос «сколько у нас таких и где они»: запросите
список с ним и `page_size=1`, в `pagination.total_items` придёт количество штук
этого вида в вашей зоне видимости.

`search` ищет по наименованию вида, а не позиции — своего наименования у позиции
нет. Поэтому опечатка в одной карточке больше не прячет её от поиска: имя
хранится в одном месте на все тридцать две штуки.

Приоритет взаимоисключающих фильтров: `unassigned`, затем `assignee_fired`,
затем `assigned_to_id`; отдельно `no_category` имеет приоритет над `category_id`.
Фильтры сужают выдачу внутри вашей зоны видимости, расширить её ими нельзя.

`no_category=1` показывает неразобранные позиции — те, чей **вид** ещё не отнесён
к категории. Ради этого категория и оставлена необязательной: пустое значение
честно означает «не разобрали», тогда как категория-заглушка вида «Прочее»
утверждала бы, что вещь классифицирована, и отличить одно от другого стало бы
невозможно. Перед закрытием инвентаризации этот фильтр должен быть пуст.

Разбирать теперь надо виды, а не позиции: проставили категорию виду (п. 1) —
разобрались разом все тридцать две штуки. Раньше то же самое требовало
тридцати двух операций.

Неразобранные позиции видит только админ организации: ответственный отвечает за
конкретную категорию, а такой предмет ещё ни к одной не отнесён.

`assignee_fired=1` закрывает щель, которую иначе не видно. Уволенный сотрудник
скрывается глобальным фильтром soft-delete, поэтому в карточке товар приходит
с `assignedTo: null` и выглядит ничьим — но во внешнем ключе владелец остался,
и в `unassigned=1` такой товар не попадёт. Этот фильтр показывает ровно их:
имущество, которое числится за уволенными и ждёт, чтобы его сняли руками.
Автоматически при увольнении ничего не снимается.

## 6. Создание товара

    POST /spa/api/inventory/items

Тело:

    {
      "nomenclatureId": 12,          // обязательно, вид товара из справочника (п. 1)
      "organizationId": 5,           // необязательно
      "userId": 51,                  // необязательно, владелец сразу при заведении
      "updId": 7,                    // необязательно, документ поступления (п. 16)
      "quantity": 10,                // необязательно, по умолчанию 1, максимум 100
      "inventoryNumber": "ОС-000451",       // необязательно
      "serialNumber": "CNB1S12345",
      "description": "Куплен взамен списанного",
      "price": 18400,
      "purchasedAt": "2024-11-12",
      "status": "in_stock"           // по умолчанию in_stock
    }

### Пачка

`quantity > 1` заводит N отдельных карточек одним запросом: приёмка по одному УПД
не должна стоить тридцати одинаковых форм. Количество нигде не хранится — это
именно N строк, каждая со своей судьбой.

Общими у пачки остаются вид, организация, владелец, документ, статус, цена, дата
приобретения и описание: десять мониторов из одной поставки приехали в один день
по одной цене. **Инвентарный и серийный номера у пачки всегда пустые** — они
уникальны у каждой штуки, и один на десять карточек упёрся бы в уникальный индекс
на второй же. Проставляют их потом, по мере наклейки бирок.

Потолок 100 — на случай, если реальная поставка окажется больше, число поднимают
в `ItemController::create`; очередь и фоновая обработка для этого не нужны.

Ответ одинаковый для любого количества:

    201  {
           "item":  {...},        // первая заведённая позиция
           "items": [{...}, ...], // все заведённые
           "created": 10
         }

`userId` проходит ту же проверку, что операция назначения (п. 8): сотрудник должен
работать в организации позиции или её подразделении. Без этого через заведение можно
было бы закрепить имущество за человеком из чужой ветки в обход `/assign`.

Позиция с владельцем получает в журнале **две** записи — `created` и `assigned`.
Иначе после первого же снятия в ленте было бы «снят с Иванова» без единого
«назначен», и как имущество к нему попало, стало бы неизвестно.

Полей `name` и `categoryId` здесь больше нет: наименование и категория живут на
виде. Нужного вида в справочнике не оказалось — заведите его отдельным запросом
(п. 1), это доступно только главному администратору.

Инвентарный номер уникален в пределах организации: у разных организаций номера
могут совпадать. Номер необязателен — предмет со стёртой биркой заводится без
него, и таких предметов в одной организации может быть сколько угодно.
Подставлять «б/н» или прочерк не нужно и вредно: второй такой предмет упрётся
в уникальный индекс.

    400  inventory_nomenclature_required | inventory_invalid_status
         inventory_invalid_price | inventory_invalid_date | inventory_invalid_quantity
    403  inventory_organization_not_allowed  организация или категория вне вашей зоны
    404  organization_not_found | inventory_nomenclature_not_found | user_not_found
    404  inventory_upd_not_found             документ не найден
    409  inventory_user_not_in_organization  сотрудник из другой ветки
    409  inventory_item_number_exists        номер занят в этой организации
    409  inventory_upd_organization_mismatch позиция вне поддерева организации документа

`updId` проходит те же проверки, что и операция привязки (п. 16): документ должен
быть виден пользователю, а организация позиции — входить в поддерево организации
документа. Заводить позицию без документа можно всегда: первичная инвентаризация
и старая мебель приехали без УПД, и это штатное состояние.

Категория проверяется по виду. Вид без категории даёт неразобранную позицию,
видную по фильтру `no_category=1`, и следствие для прав прежнее: такая позиция
не входит в зону ответственного за категорию, поэтому завести её может только
админ организации. Ответственный обязан выбрать вид со своей категорией, иначе
получит `inventory_organization_not_allowed`.

`organizationId` можно не передавать. Позиция без организации ничьей зоне не
принадлежит: её видит и ведёт только главный администратор, у остальных она
не попадает ни в списки, ни в выгрузку. Это состояние для заливки данных, а не
рабочий сценарий — обычную позицию заводите с организацией.

## 7. Редактирование карточки

    PATCH /spa/api/inventory/items/{id}

Меняет только поля карточки. Владелец, статус, организация и вид товара через
этот метод не меняются — для них отдельные операции (пп. 8–11), потому что у
них другие права и каждая обязана оставить запись в истории.

Тело — любое подмножество:

    {
      "inventoryNumber": "ОС-000451",
      "serialNumber": "CNB1S12345",
      "description": "…",
      "price": 18400,
      "purchasedAt": "2024-11-12"
    }

Полей `name` и `categoryId` здесь нет. Наименование правится у вида (п. 1) и
меняется сразу у всех его позиций — переименовать одну штуку нельзя. Если
переименовать нужно именно её, значит это другой вид: переведите позицию
операцией из п. 11.

`price`, `purchasedAt` и `inventoryNumber` очищаются передачей `null` или
пустой строки. Нечисловая цена и дата не в формате `YYYY-MM-DD` дают ошибку,
а не тихое обнуление поля.

    200  { "item": {...} }
    400  inventory_invalid_price | inventory_invalid_date
    409  inventory_item_number_exists

## 8. Назначение и снятие

    POST /spa/api/inventory/items/{id}/assign
    POST /spa/api/inventory/items/{id}/unassign

Тело для назначения:

    { "userId": 51 }

Снятие тела не требует.

Назначить можно только сотрудника организации товара или её дочерних

    200  { "item": {...} }
    403  access_denied
    404  user_not_found | inventory_item_not_found

Повторное назначение того же сотрудника и снятие с уже свободного товара
проходят без ошибки и без новой записи в истории.

## 11. Смена вида товара

    POST /spa/api/inventory/items/{id}/nomenclature   только админ организации

Пришла на место смены категории. Категория теперь свойство вида, поэтому
«перенести монитор в другую категорию» означает перевести его на другой вид.
Этой же операцией правится ошибка при заведении: выбрали не тот вид — переведите.

Тело:

    { "nomenclatureId": 31 }   // обязателен, снять вид нельзя

    200  { "item": {...} }     — и когда менять нечего, вид тот же
    400  inventory_nomenclature_required
    403  access_denied
    404  inventory_nomenclature_not_found

Вид обязателен: без него у позиции не осталось бы наименования. «Снять вид», как
раньше снимали категорию, нельзя — если позицию надо вернуть в неразобранные,
снимите категорию у самого вида (п. 1).

В историю попадёт запись `nomenclature_changed` с комментарием вида
`Монитор RDW2401K → Монитор Philips 271V8LA`. Категория приезжает вместе с видом
и отдельным событием не пишется.

Ответственному за категорию операция закрыта намеренно: иначе он мог бы вывести
имущество из своей зоны ответственности или забрать чужое.

## 14. Выгрузка в Excel

    GET /spa/api/inventory/export/items

Принимает те же query-параметры, что и список товаров (п. 4), кроме `page` и
`page_size`. Выгружается ровно то, что вы видите на экране с этими фильтрами:
скоуп применяется тот же самый, файл собирается тем же запросом. Ответственный
за категорию получит свою категорию по своему поддереву, админ организации —
всё поддерево, главный администратор — что запросил.

Ответ — файл `.xlsx` с заголовком:

    Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
    Content-Disposition: attachment; filename=inventory_2026-08-03.xlsx

Колонки, по порядку:

    ID | Инвентарный номер | Наименование | Категория | Организация |
    Серийный номер | Статус | Владелец | Цена | Дата приобретения | УПД | Описание

Числами записываются только ID и цена, всё остальное — строками, чтобы Excel
не съел ведущие нули в инвентарных номерах вида `0012`. Дата приобретения —
текстом в формате `YYYY-MM-DD`. Статус — русской подписью, не кодом.
Колонка «УПД» — человекочитаемая подпись документа вида `УПД №УТ-1043
от 12.11.2024`, у позиций без документа пустая.

Колонка «Наименование» берётся с вида товара — у позиции своего наименования нет.
Одинаковые вещи в выгрузке теперь называются одинаково, и сводная по ним в Excel
собирается обычной сводной таблицей.

Пустые ячейки означают ровно то же, что `null` в API: у позиции нет номера,
владельца, организации, а у её вида — категории. Пустая «Категория» — это
неразобранный вид.

Ограничение: не более 10000 строк за раз. При превышении вернётся JSON, а не
файл — сузьте фильтр:

    409  { "error": "inventory_export_too_large", "total": 24500, "limit": 10000 }

    403  inventory_no_access   нет ни одной привязки

### Как забрать файл с фронта

Обычная ссылка `<a href download>` не подойдёт: браузер не отправит по ней
заголовок `Authorization`, а SPA API работает на stateless JWT. Забирать нужно
через `fetch` и превращать ответ в Blob:

    const response = await fetch("/spa/api/inventory/export/items?organization_id=2", {
      headers: { Authorization: `Bearer ${token}` }
    });

    if (!response.ok) {
      const { error, total, limit } = await response.json();
      // показать сообщение, например «слишком много строк: total из limit»
      return;
    }

    const blob = await response.blob();
    const url = URL.createObjectURL(blob);
    const link = document.createElement("a");
    link.href = url;
    link.download = "inventory.xlsx";
    link.click();
    URL.revokeObjectURL(url);

Проверять `response.ok` обязательно: при отказе приходит JSON с тем же
статус-кодом, и без проверки пользователь скачает файл с текстом ошибки внутри.

### Про будущий импорт

Набор и порядок колонок выгрузки заданы как формат будущего импорта: файл
выгружается, правится в Excel и заливается обратно. Первая колонка `ID` нужна
именно для этого — по ней импорт отличит правку существующей позиции от новой
строки. У новых строк колонку `ID` оставляют пустой.

Самого импорта пока нет.

## 15. Справочники для форм

    GET /spa/api/inventory/references/organizations

Организации, доступные текущему пользователю, уже вместе с потомками. Главный
администратор получает все.

    {
      "organizations": [
        { "id": 2, "name": "ДонСтройМаш", "fullName": "ООО «ДонСтройМаш»",
          "path": "ДонСтройМаш", "parentId": null },

          "path": "ДонСтройМаш / Бухгалтерия", "parentId": 2 }
      ]

`parentId` позволяет собрать дерево на фронте без дополнительных запросов.

    GET /spa/api/inventory/references/users?organization_id=5

Сотрудники **ровно этой организации**, без дочерних. Уволенные отсекаются.

Дочерние намеренно не подтягиваются: дерево организаций фронт показывает целиком,

можно сделать только сотрудника организации товара или её потомка (п. 8), а этот

    {

        {

          "patronymic": "Сергеевич", "login": "ivanov_ps", "organizationId": 5
        }
      ]
    }

    400  organization_required                параметр не передан
    403  inventory_organization_not_allowed   организация вне вашей зоны

## 16. УПД — документы поступления

Универсальный передаточный документ: то, по чему имущество приехало. Заводится
раньше позиций — по одному УПД приходит партия, и документ должен существовать
до того, как к нему привяжут первую вещь. Скан при этом лежит в одном экземпляре,
а не копией у каждой из тридцати позиций.

Файлов у документа сколько угодно: скан бывает постраничным, к нему прикладывают
спецификацию. Принимаются `pdf`, `png`, `jpg`, `jpeg`, `webp`, `docx`, `xlsx`,
не больше 25 МБ на файл. Расширение сверяется с сигнатурой содержимого, поэтому
переименованный `.exe` не пройдёт.

### Видимость

Документ принадлежит организации-получателю и виден целиком её админу
инвентаризации и админу любой родительской организации в поддереве. Главный
администратор видит все. Ответственный за категорию **документов не видит вовсе**:
список приходит пустым, обращение по id вернёт `access_denied`.

При этом номер и дату он видит — в поле `upd` на карточке своей позиции (п. 4
и п. 5). Там компактная ссылка без файлов, ровно чтобы карточка не выглядела
сломанной. Файлы доступны только через эндпоинты этого раздела.

Право смотреть и право править здесь совпадают по множеству людей, поэтому
проверка одна: админ организации документа.

### Список

    GET /spa/api/inventory/upd

    page, page_size       как везде, по умолчанию 20
    organization_id       организация-получатель, по умолчанию с потомками
    only_own_organization 1 — без дочерних
    date_from, date_to    период по дате документа, YYYY-MM-DD
    search                по номеру и поставщику

Мусор в `date_from` и `date_to` игнорируется: это сужение выборки, а не ввод
данных, ронять список из-за кривого query-параметра незачем.

Ответ:

    {
      "upd": [
        {
          "id": 7,
          "number": "УТ-1043",
          "date": "2024-11-12",
          "supplier": "ООО «Ромашка»",
          "label": "УПД №УТ-1043 от 12.11.2024",
          "organization": {
            "id": 2, "name": "ДонСтройМаш", "fullName": "ООО «ДонСтройМаш»",
            "path": "ДонСтройМаш"
          },
          "createdBy": { "id": 1, "login": "admin" },
          "createdAt": "2026-08-04T10:15:00+03:00"
        }
      ],
      "pagination": { ... },
      "canManage": true
    }

`canManage` — может ли текущий пользователь заводить документы. У ответственного
за категорию `false`: роль пускает его на экран, но список пуст, а создание
вернёт 403. Фронту флаг нужен, чтобы не рисовать кнопку, обречённую на отказ.

### Карточка с файлами

    GET /spa/api/inventory/upd/{id}

    {
      "upd": { ..., "itemsCount": 12 },
      "files": [
        {
          "id": 3,
          "filename": "УПД 1043 стр1.pdf",
          "contentType": "application/pdf",
          "sizeBytes": 284431,
          "uploadedBy": { "id": 1, "login": "admin" },
          "createdAt": "2026-08-04T10:16:00+03:00"
        }
      ]
    }

    403  access_denied
    404  inventory_upd_not_found

Что именно приехало по документу — отдельным запросом к списку товаров
с фильтром `upd_id` (п. 4). Так позиции приходят с обычным скоупом, пагинацией
и всеми прочими фильтрами, а карточка не дублирует их форматирование.

### Создание

    POST /spa/api/inventory/upd

    {
      "number": "УТ-1043",
      "date": "2024-11-12",
      "supplier": "ООО «Ромашка»",   // необязательно
      "organizationId": 2
    }

    201  { "upd": {...} }
    400  inventory_upd_number_required | inventory_invalid_date
    403  inventory_organization_not_allowed
    404  organization_not_found

Уникальности номера нет: разные поставщики законно выдают документы с одинаковыми
номерами. Дата проверяется строго — «2026-02-31» отвергается, а не переполняется
в 3 марта.

### Правка

    PATCH /spa/api/inventory/upd/{id}

Меняются `number`, `date`, `supplier`. **Организация не меняется**: позиции уже
привязаны и проверялись на вхождение в её поддерево, смена получателя задним
числом сделала бы часть из них невалидными молча. Ошиблись организацией —
документ заводится заново.

    200  { "upd": {...} }
    400  inventory_upd_number_required | inventory_invalid_date
    403  access_denied
    404  inventory_upd_not_found

### Удаление

    DELETE /spa/api/inventory/upd/{id}

    200  { "success": true }
    403  access_denied
    404  inventory_upd_not_found
    409  inventory_upd_has_items  + "itemsCount"

Удаляется только документ без позиций — как категория без имущества. Файлы
сносятся вместе с ним, из хранилища тоже.

### Файлы

    POST   /spa/api/inventory/upd/{id}/files            multipart, поле `file`
    DELETE /spa/api/inventory/upd/{id}/files/{fileId}
    GET    /spa/api/inventory/upd/{id}/files/{fileId}   скачивание потоком

    201  { "file": {...} }
    400  inventory_file_upload_failed         файла в запросе нет
    403  access_denied
    404  inventory_upd_not_found | inventory_file_not_found
    415  inventory_file_too_large | inventory_file_type_not_allowed

Файл ищется в пределах своего документа: подставив чужой `fileId` к своему
`{id}`, вложение соседнего УПД не скачать.

Скачивание отдаёт поток с `Content-Disposition: attachment`, ссылкой его не
забрать — браузер не отправит по ней `Authorization`. Тянуть нужно так же, как
выгрузку в Excel: запросом с заголовком, затем blob (см. п. 14).

Запрос крупнее `post_max_size` PHP выбрасывает целиком, файла в нём не окажется
вовсе — придёт `inventory_file_upload_failed`, а не «слишком большой». Поэтому
свой лимит в 25 МБ стоит заметно ниже потолка PHP.

### Привязка позиции к документу

    POST /spa/api/inventory/items/{id}/upd

    { "updId": 7 }      // null или 0 — отвязать, позиция остаётся

Отдельная операция, а не поле карточки: у неё другие права и обязательная запись
в историю (действие `upd_changed`). Доступна **админу организации**, как перенос
и смена вида — ответственный за категорию документов не видит, выбирать ему
было бы не из чего.

Позиция обязана числиться за организацией документа или её потомком, иначе по
документу для одного филиала заводилось бы имущество другого.

    200  { "item": {...} }   — и когда менять нечего, документ тот же
    403  access_denied                            позиция или документ вне вашей зоны
    404  inventory_upd_not_found
    409  inventory_upd_organization_mismatch      позиция вне поддерева документа

## 17. Удаление позиции

    DELETE /spa/api/inventory/items/{id}      только ROLE_ADMIN

    200  { "success": true }
    403  нет ROLE_ADMIN
    404  inventory_item_not_found

Удаление физическое и необратимое: вместе с позицией уходит её журнал движений
(внешний ключ истории стоит `ON DELETE CASCADE`). Ни статус, ни владелец, ни
привязка к УПД удалению не мешают — проверок здесь нет, поэтому подтверждение
на фронте обязательно.

Это ручка для ошибок ввода: завели пачку в сто штук вместо десяти, продублировали
поставку по одному УПД, залили тестовые данные на боевом стенде. **Штатное
выбытие имущества — статус `written_off` (п. 9)**: списанная вещь остаётся в базе
вместе с историей, и инвентаризация прошлых лет по ней сходится. Удалённая
позиция не сходится ни с чем — её больше нет.

Права здесь строже, чем во всём остальном модуле: `ROLE_INVENTORY_ADMIN` не
подходит, нужен именно `ROLE_ADMIN`. Главный администратор инвентаризации ведёт
справочники и распоряжается имуществом во всех организациях, но все его действия
обратимы — списание отменяется сменой статуса, ошибочный вид переводом позиции.
Удалённую позицию восстановить нечем, поэтому ключ от этой ручки лежит у общего
администратора системы.

Массового удаления нет: позиции сносятся по одной. Порядок при чистке вида
строго такой — сначала все его позиции этой ручкой, потом сам вид (п. 1). Пока
жива хотя бы одна позиция, вид не удалится: внешний ключ стоит
`ON DELETE RESTRICT`, и удаление вида вернёт 409 со счётчиком.

## Чего пока нет

Не реализовано осознанно, будет отдельным этапом:

    - слияние двух видов товара в один
    - импорт xlsx (выгрузка уже есть, см. п. 14 — она же задаёт формат файла)
    - массовые операции (назначить/сменить статус пачкой)
    - уведомления при назначении товара
    - подтверждение получения сотрудником
    - печатные формы актов передачи

Слияние стоит первым не случайно. Уникальный индекс справочника ловит только
регистр, а дубли рождаются и другими способами: «Клавиатура компьтерная» против
«компьютерная», латинская `K` вместо кириллической `К` в «Монитор RDW2401K».
Свести такую пару сейчас можно только переводом позиций по одной (п. 11) с
последующим удалением опустевшего вида — на тридцати двух мониторах это
тридцать две операции. Ручка `merge` закроет это одним запросом.

## Разовая настройка

Перед первым запуском модуля нужна одна команда, идемпотентная:

    php bin/console app:roles:sync       создаст строки ролей инвентаризации
                                         в таблице role

Больше ничего заводить не нужно. Оба справочника наполняет главный
администратор через API, предустановленных значений нет.

С пустым справочником категорий модуль работает: виды просто заводятся
неразобранными. А вот **с пустым справочником видов завести позицию нельзя** —
`nomenclatureId` обязателен. Первое, что делает главный администратор на новом
стенде, — создаёт виды товара (п. 1).

## Связь с разделом организаций

Организацию, за которой числится имущество, удалить нельзя — попытка вернёт
сообщение с количеством позиций. Ограничение живёт в контроллере организаций,
не в этом модуле.

Причина: организации удаляются мягко (Gedmo SoftDeleteable), поэтому внешний
ключ с `ON DELETE RESTRICT` не срабатывает, и запрет приходится держать в коде.
Без него имущество осталось бы в базе, но в списках показывалось бы с
`organization: null` — организацию скрывает глобальный фильтр soft-delete, а
внешний ключ у позиции остаётся заполненным, и отличить такую строку от честно
заведённой без организации стало бы нельзя. Прежде чем удалять организацию,
перенесите имущество (п. 10) или спишите его (п. 9).

Дочерние организации при удалении родителя выживают: у них сбрасывается
родитель, и их имущество остаётся при них.

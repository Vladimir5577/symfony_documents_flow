ВНУТРЕННИЙ API СПРАВОЧНИКОВ ДЛЯ go_warehouse_service
=====================================================

Дата: 2026-07-29
Код: src/Controller/InternalApi/WarehouseReferenceController.php
Потребитель: go_warehouse_service/internal/client/symfony_client.go


1. ЗАЧЕМ ЭТО СУЩЕСТВУЕТ
-----------------------

Складской микросервис держит РЕПЛИКУ справочника пользователей. Наполняется
она двумя путями, и второй обязателен:

  а) события RabbitMQ user.upserted / user.deleted (уже публикуются
     UserSyncEntityListener, менять его не надо);
  б) разовая массовая загрузка при старте — ЭТОТ эндпоинт.

Почему (б) нельзя выбросить: события описывают только ИЗМЕНЕНИЯ, а topic
exchange выбрасывает сообщение, если под него ещё нет очереди. Всё, что монолит
опубликовал до первого запуска консьюмера складского сервиса, потеряно.
Без стартовой загрузки реплика остаётся ПУСТОЙ.

Канбану это безразлично — он знает user_id из своих таблиц. Складской сервис
матчит сотрудников ПО ФИО из выгрузок 1С, и на пустой реплике первый импорт
МЦ.04 не свяжет ни одного из 163 сотрудников: все строки лягут с ФИО текстом,
а связи с пользователями портала не будет. Экран при этом работает, отчёты
работают, и заметить это трудно.


2. ПОЧЕМУ ОТДЕЛЬНЫЙ КОНТРОЛЛЕР, А НЕ РАСШИРЕНИЕ KanbanUserController
--------------------------------------------------------------------

Разные контракты у разных потребителей:

  KanbanUserController   GET /api/internal/kanban/users?ids=1,2,3   — точечно
  WarehouseReference     GET /api/internal/warehouse/users          — весь список

Расширение канбановского эндпоинта связало бы два сервиса, которые ничего друг
о друге знать не должны, и любая правка контракта канбана ломала бы склад.

Ключи тоже РАЗНЫЕ (kanban_internal_api_key и warehouse_internal_api_key):
компрометация ключа одного сервиса не должна открывать справочники другому.


3. КОНТРАКТ
-----------

Файрвол на ^/api/internal отключён (config/packages/security.yaml:23-25),
доступ закрывает заголовок X-API-Key, проверяемый в самом контроллере.

  GET /api/internal/warehouse/users
  Заголовок: X-API-Key: <warehouse_internal_api_key>
  Ответ 200: [
    {"id":1,"login":"ivanov","lastname":"Иванов","firstname":"Иван",
     "patronymic":"Иванович","deleted_at":null}
  ]

  GET /api/internal/warehouse/departments
  Ответ 200: [
    {"id":10,"name":"ИНФОРМАЦИОННО-ТЕХНИЧЕСКИЙ ОТДЕЛ","parent_id":2,
     "type":"department"}
  ]

  Отказ (нет ключа, неверный ключ, ключ не задан в окружении):
  403 {"error":"Access Denied"}

Формат ответа — голый JSON-массив, БЕЗ обёртки {resource, pagination}.
Это осознанное отклонение от конвенции SpaApi: внутренний межсервисный
контракт, повторяет форму KanbanUserController.


4. ГРАБЛИ, КОТОРЫЕ НАДО ЗНАТЬ
-----------------------------

deleted_at ВСЕГДА null.
  Глобальный фильтр Gedmo SoftDeleteable включён (doctrine.yaml), и findAll()
  удалённых не отдаёт. «Надгробия» уволенных приходят в складской сервис только
  событием user.deleted через RabbitMQ. Поле оставлено в ответе ради
  совместимости формы с KanbanUserController — но полагаться на него нельзя.

/departments отдаёт ВСЕ организационные единицы, не только Department.
  В выгрузках 1С подразделение приходит СТРОКОЙ, и заранее неизвестно, какому
  уровню иерархии она соответствует. Если вернуть только отделы, строка,
  за которой стоит филиал, не сматчится. Тип единицы — в поле type
  (organization | filial | department).

name физически лежит в колонке short_name.
  Single-table inheritance на таблице organization, дискриминатор в колонке
  discriminator. При отладке SQL помнить обязательно.

Параметр объявлен через default::, а не resolve:.
  warehouse_internal_api_key: '%env(default::WAREHOUSE_INTERNAL_API_KEY)%'
  Если переменная не задана, параметр пуст, контроллер отвечает 403,
  а контейнер продолжает собираться. С resolve: отсутствие переменной уронило
  бы всё приложение целиком.

Проверка ключа — hash_equals, а не !==.
  Сравнение секретов должно идти за постоянное время, иначе ключ подбирается
  посимвольно по времени ответа. (В KanbanUserController используется !== —
  это его существующее поведение, здесь оно не воспроизводится.)


5. ЧТО НУЖНО СДЕЛАТЬ ПРИ РАЗВЁРТЫВАНИИ
--------------------------------------

  1) В .env монолита добавить:
       WAREHOUSE_INTERNAL_API_KEY=<длинная случайная строка>
     Сгенерировать: openssl rand -hex 32
     Без этого оба эндпоинта отвечают 403 — это штатное поведение, не поломка.

  2) То же значение прописать складскому сервису:
       SYMFONY_INTERNAL_API_KEY=<то же самое>
       SYMFONY_INTERNAL_API_URL=http://nginx_web:80

  3) Проверить:
       curl -H "X-API-Key: <ключ>" http://nginx_web/api/internal/warehouse/users
     Должен вернуться непустой массив. Пустой массив означает, что реплика
     складского сервиса наполнится пустой и импорт никого не сматчит.


6. ЧЕГО ЗДЕСЬ НЕТ И НЕ ДОЛЖНО БЫТЬ
----------------------------------

Пагинации. Сотрудников порядка сотен, организационных единиц — десятки;
потребителю нужен весь список разом для построения карты «ФИО → id».
Постраничная выдача здесь только усложнила бы обе стороны.

Фильтров и поиска. Матчинг делает потребитель у себя, по нормализованному ФИО.

Записи. Эндпоинты только на чтение: складской сервис не владеет ни
пользователями, ни оргструктурой.

0. КОНТЕКСТ И ПРИНЯТЫЕ РЕШЕНИЯ
--------------------------------------------------------------------------------
Модуль почти автономен уже сейчас: обратная зависимость ровно одна
(OrganizationController.php:428), в templates/ ноль упоминаний, каскадов Doctrine
нет, все связи наружу — однонаправленные ManyToOne. Внешних FK две таблицы:
"user" (10 FK) и organization (3 FK).

Отличие от канбана, определяющее объём работ: канбану хватило реплики
пользователей из 7 полей. Инвентаризации нужно ДЕРЕВО ОРГАНИЗАЦИЙ, потому что
по нему считается видимость (InventoryScope разворачивает поддерево). События
organization.* в монолите нет — его надо написать.

ТЕРМИНОЛОГИЯ (чтобы не переспорить это в третий раз): сервис с несколькими
модулями внутри — это модульный монолит, общепринятая и рабочая форма, а не
компромисс. Сервис — единица ДЕПЛОЯ И ВЛАДЕНИЯ, модуль — единица МОДЕЛИРОВАНИЯ
домена; это разные оси, и их смешение как раз и есть типовая ошибка. Вопрос не
в числе модулей на сервис, а в том, настоящая ли граница между ними. Проверка
одна: можно ли вынести модуль за день (см. раздел 3, пункт 1.1).

РЕШЕНО:
  - Один сервис. Закупки НЕ переносим: они работают в монолите, перенос
    работающего кода без причины — расход. Но реплику, консьюмеры и работу с
    деревом делаем ОТДЕЛЬНЫМ ПАКЕТОМ, не сросшимся с доменом инвентаризации,
    чтобы решение о переезде закупок осталось дешёвым.
  - Реплика users + organization, БЕЗ FK на них из доменных таблиц (порядок
    сообщений не гарантирован — ссылка может приехать раньше объекта).
  - Механика выдачи ROLE_INVENTORY_MANAGER упраздняется: сервис не может писать
    в таблицу role монолита. Роль всегда была кэшем гейта, права считает скоуп.
  - Doctrine-миграции в монолите (фаза 5) генерирует ПОЛЬЗОВАТЕЛЬ САМ.
    Миграции сервиса (goose) — часть репозитория сервиса, их пишем.

ЧЕСТНАЯ ОЦЕНКА: это не портирование, а переписывание 4263 строк рабочего PHP
на Go. Недели, не дни. Фазы 0-1 полезны сами по себе и переиспользуются любым
следующим сервисом; фаза 2 — чистая стоимость выноса.

[ ] 0.3 Расширить UserSyncMessage: organizationId, workerStatus, profession,
        hiredAt, roles (плоский массив строк ROLE_*).
        ОБЯЗАТЕЛЬНО добавить 'organization' в WATCHED_FIELDS — забытое поле в
        этом списке даёт тихий дрейф, худший вид поломки.
        Go-консьюмер канбана лишние JSON-поля игнорирует, не сломается.
        Каталог ролей (таблица role с описаниями) НЕ реплицировать — сервису
        нужны назначения, а не справочник; подписи ролей знает фронт.
        PAYLOAD ЕДИНЫЙ НА ВСЕХ ПОТРЕБИТЕЛЕЙ — сообщение одно, exchange разносит
        его по очередям, каждый берёт нужное. Разные сообщения под разных
        подписчиков не делать: монолиту пришлось бы знать их поимённо, и
        односторонняя зависимость, ради которой всё построено, исчезнет.
        Расширять payload безопасно: канбан читает его обычным json.Unmarshal
        без DisallowUnknownFields (consumer.go:260), незнакомые поля отбросит.
        СЛЕДСТВИЕ, ВАЖНОЕ ДЛЯ СОСТАВА: payload — широковещательный. Всё, что в
        него положено, видит каждый нынешний и будущий потребитель и лежит в
        durable-очередях. Это главный довод против «копируем всё» — не размер
        реплики, а то, что почта и телефон уехали бы во все сервисы разом.

[ ] 0.4 Листенеры на смежные сущности — обе диспатчат ТОТ ЖЕ UserSyncMessage
        для затронутого пользователя, отдельных таблиц в реплике у них нет:
        - Worker (postPersist/postUpdate/preRemove) -> $worker->getUser();
        - UserRole (join-сущность назначения роли) -> $userRole->getUser().
          Без неё роли не поедут вообще: они лежат в отдельной таблице, и
          выдача роли НЕ делает сущность User грязной, то есть postUpdate на
          User не сработает.
        Итого источников одного сообщения три (User, Worker, UserRole) —
        поэтому билдер из 0.2 обязателен, иначе состав payload разъедется.

ЧТО ВСЁ-ТАКИ ИЗМЕНИТСЯ (не поломка, но знать):
  - событий станет больше: user.upserted полетит ещё при смене организации,
    правке воркера и выдаче роли. Канбан на каждое сделает холостой апсерт
    своих 7 полей;
  - ImportWorkersFromExcelCommand даст всплеск: массовый импорт идёт через
    Doctrine, значит по сообщению на каждого воркера, тысячи разом;
  - ресинк рассылает всем подписчикам сразу. Сейчас их два: kanban.user_sync
    и notification.user_sync — сервис нотификаций держит СВОЮ реплику
    пользователей на тех же событиях (живое подтверждение того, что реплика
    на сервис — рабочая схема, а не теория). Оба потребителя на месте
    (проверено 2026-08-06). Если какой-то сервис лежит, сообщения дождутся
    его в durable-очереди без TTL, но поднять всё лучше ДО ресинка.
ПРЕДОСТОРОЖНОСТЬ: definitions.json — файл НАЧАЛЬНОГО импорта. Перезаливка в
живой брокер: очереди объявляются идемпотентно, а политики заменяются
целиком. Проще добавить очереди и политику через management UI, а файл
править для чистой среды.

СОПУТСТВУЮЩАЯ ЗАДАЧА В РЕПОЗИТОРИИ КАНБАНА (не входит в фазу 0, но её же
тема). В internal/repository/user_repository.go:142 добавить к
ON CONFLICT DO UPDATE клаузу пропуска холостых записей (форма — см. 1.4,
явный кортеж без synced_at). Смысл не в мёртвых кортежах, их на 7704 строках

КОГДА ЗАПУСКАТЬ РЕСИНК (решено 2026-08-05, по расписанию НЕ ставим):

Ночной cron — только если месяц ручных запусков покажет дрейф, которого вы
не создавали руками. Молчаливый cron маскирует сломанный листенер.
